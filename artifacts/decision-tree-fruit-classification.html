Introduction

This artifact is a written algorithm. The assignment asked for a theoretical, step-by-step account of how one classification method would sort the Kaggle Fruits Classification dataset, with every decision point and criterion spelled out in plain English. I chose a decision tree and wrote the full process as a technical report, from the first look at the data to the evaluation of the finished model, including a worked example in which the Gini impurity arithmetic behind each split is shown by hand.

Description

The report has six parts. A short section describes how large language models predict text at a high level, to set the fruit problem in the wider context of prediction. The dataset section establishes what the Kaggle data really is (10,000 photographs of apples, bananas, grapes, mangoes, and strawberries, split 97/2/1 into training, validation, and test folders) and how each photograph would be reduced to six measurable attributes such as dominant hue, aspect ratio, relative size, and surface texture. The method section explains how a decision tree learns, why it fits this labeled dataset, and why K-means clustering was not chosen.

The core of the report is a fifteen-step process in four phases: preparing the data, growing the tree, stopping and pruning, and classifying a new fruit. Ten hypothetical fruits carry the worked example; three candidate root questions are scored and compared in a table, and the resulting tree is drawn as Figure 1. Tables list the parameter settings a practitioner would choose (with the scikit-learn name and the reason for each value), the decision points and their effect on the final label, the evaluation metrics and how each would be read, and the implementation challenges with their solutions. The report closes with the patterns the evaluation should reveal, such as bananas being the easiest class and red apples and strawberries the most likely confusion.

Objective

The assignment's outcomes were to describe how LLMs work at a high level, to explain the characteristics and uses of decision trees and K-means clustering, and to construct a clear, logical algorithm for classifying data. My own objective was to practice the discipline of writing a method down so completely that someone else could carry it out without me, which is the same discipline that design documents and runbooks demand in engineering work.

Process

  1. Read the assignment and rubric side by side and mapped each rubric criterion (method justification, implementation process, results, instruction quality, presentation) to a section of the report before writing anything.
  2. Examined the Kaggle dataset's data card and found that it is an image collection, not the table of size, color, and weight the assignment wording implied. Rather than gloss over that, I made the gap part of the report: a section on how pixels become attributes a tree can split on.
  3. Chose the decision tree over K-means because the data are labeled, the fruits separate along simple thresholds, and a tree's questions map directly onto the "decision points" the assignment asked for.
  4. Designed a ten-fruit worked example with realistic attribute values, computed the Gini impurity of the root and of three candidate splits by hand, and discovered that balanced classes produce ties between equally clean splits. I kept the tie in the report and explained how the algorithm breaks it, since that is what a reader would meet on real data.
  5. Drew the resulting tree as a figure with matplotlib, then wrote the fifteen steps, the parameter table, the decision-point table, the evaluation plan, and the challenges table.
  6. Built the document in APA 7 student format (title page, running page numbers, double spacing, APA-style tables and figure, hanging-indent references) and rendered it to PDF to check pagination, orphaned headings, and table breaks, fixing each before delivery.

Tools and technologies used

  • Kaggle Fruits Classification dataset (data card and folder structure) as the subject
  • Python 3 with matplotlib for the decision tree figure
  • docx-js (Node.js) to generate the Word document, with LibreOffice for the PDF rendering check
  • scikit-learn's DecisionTreeClassifier parameter names as the vocabulary for the parameter table
  • APA 7 style for the document, tables, figure, and references
  • Claude (Anthropic) as a drafting and review assistant for the text, the Gini arithmetic check, and the document build

Value proposition

For an employer, this artifact shows that I can explain a machine learning method at the level of individual decisions, with the arithmetic exposed, in language a non-specialist can follow. That matters whenever a model has to be reviewed, audited, or handed to another team. It also shows the habit of checking an assignment's assumptions against the real data and documenting the gap honestly instead of writing around it. Both support my personal value proposition: dependable production AI depends on people who can state exactly what a model does and why.

Unique value

Three things set this report apart from a standard description of decision trees. It bridges an image dataset to a tabular method by specifying the feature extraction step, which most write-ups of this assignment skip. It works the Gini impurity through by hand on a concrete example and shows a real tie between candidate splits rather than a textbook case where one split obviously wins. And it treats the theoretical exercise as if it were going to be run: parameter values with reasons, an evaluation protocol that uses the dataset's own validation and test folders, and a table of implementation problems with their fixes.

Relevance

Decision trees and their ensembles (random forests, gradient boosting) remain the strongest tools for tabular data, which is most of the data in a bank. The feature extraction section is the same thinking I apply when deciding whether a retrieval pipeline needs a learned model or a set of explicit rules. The report also covers the first AIML-501 outcome on how LLMs work, which connects directly to my current work on retrieval-augmented generation.
